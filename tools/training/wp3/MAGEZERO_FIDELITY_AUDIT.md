# MageZero Fidelity Audit — our deployment vs upstream (WillWroble/MageZero)

Date: 2026-08-01. Scope: local MageZero clone (working tree on `main`, no local
commits — all our changes are uncommitted edits + new files), stock upstream
XMage release jars, and the live curriculum run started 2026-07-29 (UWTempo
ver1, currently crash-looping in gen 1). All numbers below are measured from
files on disk or from the run's own logs. Paths are relative to the MageZero
repo root (`<mz>`).

Thesis under test: "MageZero is proven upstream; if we see no improvement, our
implementation deviates." Verdict: **the implementation deviates in 13 places,
and two of them fully explain the observed stall** — (1) a device-selection
regression we introduced crashes the pipeline at the eval stage after every
gen-1 generation cycle, so no training step has run since 2026-07-29 11:40;
(2) the replay buffer is glob-based, so the ~4 crash-looped gen-1 attempts have
piled up ~597K duplicate training states that the next training step WILL
consume.

---

## 1. Replay-buffer pollution audit — VERDICT: POLLUTED (by design of the data path)

### 1.1 Mechanism (code, not speculation)

- `runner.py:run_train()` invokes `train.py --deck --version --epochs
  [--checkpoint]` — **no session list is passed**.
- `train.py:train()` builds its dataset as
  `H5Indexed(f"data/{deck}/ver{version}/training")`, and `dataset.py:H5Indexed`
  loads **every** `*.h5`/`*.hdf5` in that directory (`Path(dir).glob`).
- `run.json` session bookkeeping is consulted in exactly one place:
  `runner.py:archive_out_of_window()`, which moves training files to `archive/`
  only if their session id appears in a **recorded (completed) gen** older than
  the replay window. Session ids from aborted attempts are never recorded, so
  their files are **never archived — they stay in `training/` for the life of
  the run**, and `replay_buffer_gens` cannot evict them.
- `runner.py:move_testing_to_training()` moves **all** `*.hdf5` from `testing/`
  to `training/` at the move stage, regardless of provenance.
- On every crash-loop restart, `next_session_id()` reserves fresh ids, so each
  aborted attempt leaves its partial/complete session files behind in
  `testing/` under new names.

Conclusion: training data is selected by **directory glob (polluted)**, not by
`run.json` bookkeeping (clean). Bookkeeping only controls window eviction, and
only for files it knows about.

### 1.3 What the next training step will consume

When the live attempt finally completes gen 1, `move_testing_to_training()`
moves everything and `train.py` will train on approximately:

- 229,086 existing training states (111,244 of them already orphan)
- \+ 597,188 aborted-attempt duplicates
- \+ ~250,000 legitimate gen-1 states (sessions 51-55)
- = **~1.08M states, of which only ~34% (gen0 117,842 + gen1 ~250K) is what the
  run design intends.** Gen-1-era games will be over-represented ~3.4:1 versus
  the intended single gen-1 contribution, and ~66% of the buffer sits outside
  `run.json` bookkeeping and is permanently unevictable by the replay window.

Pollution has already happened once: gen-0 training was 48.6% carry-over from
earlier runs (`start_from_version: 1` also re-seeded the model from a
checkpoint trained on those earlier runs, so "gen 0" was never a clean
baseline).

### 1.4 Why gen 1 crash-loops (root cause, measured)

`runs/2026-07-29_03-19-18/test.log` shows two identical crashes (2026-07-30
02:47 and 2026-07-31 16:41), both at the `eval_previous_model` stage
(`run_test`, `check=True` — a crash here kills the runner **after** generation
but **before** move/train):

```
RuntimeError: Expected all tensors to be on the same device, but got index is
on cpu, different from other tensors on cuda:0
```

Cause: our new `src/magezero/device.py` re-evaluates `device()` **per call**
and returns `"cuda"` only when >4 GB VRAM is free. In `test.py`, the model is
created while enough VRAM is free (`.to(_dev())` → cuda), the ~3.8 GB
checkpoint then lands on the GPU, free memory drops below the 4 GB threshold,
and every subsequent per-batch `_dev()` call returns `"cpu"` — batches stay on
CPU against a CUDA model. This is deterministic on the shared GPU and **will
crash the live attempt again** when session 55 finishes, wasting another full
generation cycle (~2.5 days at current throughput), unless fixed first.
`device.py`, `test.py`, `train.py` are unchanged since 2026-07-28/29, so the
bug is still in place. `train.py` uses the same per-call pattern and is
exposed to the same flapping mid-epoch.

## 2. Hyperparameter / behavior deviations vs origin/main

Upstream = `origin/main` (HEAD == our local HEAD; every local change is an
uncommitted working-tree edit). Java side: our `xmage/lib/mage-player-ai-*.jar`
are the stock 2026-04-18 release binaries — **no Java-side deviations**.

| # | Param / behavior | Upstream | Ours | Impact |
|---|---|---|---|---|
| 1 | `game.yml mcts.search_budget` | 1000 | **300** | Weaker search targets; README throughput figures were measured at 300, but the author ships 1000 |
| 2 | `run.yml games_per_gen` | 100 (author's run.yml); 200 (setup-guide default) | **550**, edited mid-crash-loop from 200 (backup file dated 2026-07-30 08:39; run.json snapshot still says 200) | 2.75-5.5x more data per gen than upstream ever validated; mixes 200- and 550-game sessions inside one gen; slows the gen cycle |
| 3 | `run.yml replay_buffer_gens` | 10 (author's run.yml); 3 (setup-guide default) | 3 | Matches guide default; deviation only vs the author's own last-used config |
| 4 | `game.yml training.threads` | 4 | **6** | Upstream README warns per-thread sims/sec degrades at 8 threads (heap pressure) |
| 5 | `run.yml generations` | 5 | 6 | Minor |
| 6 | `run.yml version/start_from_version` | 20/20 (fresh version per run) | **1/1** — re-uses ver1's dirty data dir and self-seeds from ver1's own checkpoint | This is what makes the orphan-file pollution possible; also means no clean bootstrap baseline |
| 7 | `src/magezero/device.py` (new file) + `test.py`/`train.py`/`dataset_stats.py` device refactor | hard `.cuda()` | dynamic per-call device with 4 GB free-VRAM threshold | **Root cause of the gen-1 crash loop** (Section 1.4) |
| 8 | `server.py MAX_WAIT_MS` | 0 (forces batch size 1) | 5 | Ours is an improvement (real batching); still a fidelity difference in eval dynamics |
| 9 | `server.py` VRAM cap + CPU `map_location` on checkpoint load | absent (server held ~17.3 GB incl. 7.6 GB optimizer state restored to GPU) | allocator capped, optimizer state kept off GPU | Improvement/neutral; measured no throughput regression |
| 10 | `train.py` checkpoint staging to local disk | writes `.tmp` next to final path (network share) | stages on local disk | Improvement (was ~20 min/epoch of network I/O); neutral to fidelity |
| 11 | `runner.py launch_jvm` | Windows-only `.bat` | per-platform `.sh`/`.bat` | Necessary Linux port; neutral |
| 12 | `runner.py` `MZ_SERVER_PYTHON`/`MZ_SERVER_ENV` — inference server on a ROCm build / separate accelerator, GPUs shared with a production vLLM container | single CUDA env, dedicated GPU assumed | split/shared | Eval serving is resource-constrained; source of timeout pressure below |
| 13 | Search-termination regime | `timeout_ms: 4000` exists upstream too, and upstream Java **does** enforce it (`ComputerPlayerMCTS2.searchTimeout`, plus a 60 s hard force and node/depth caps) — upstream is budget-bound on healthy serving | **34.2% of our searches end by timeout** (measured over the last ~30 MB of `xmage/magezero.log*`: 1,031 "timed out, ending search" vs 1,980 "required visits reached") even at budget 300 | A third of decisions get fewer than 300 sims; upstream's results assume the budget is normally reached |

**Explicitly NOT deviations** (questions from the brief, resolved):

- **td_discount 0.85 vs 0.95 — which wins?** The runner wins for the learning
  agent: `build_game_yml()` overwrites `player_a.mcts.td_discount` with the
  curriculum value each gen (`configs/curriculum.yml` schedule: gen0 0.95,
  gen1 0.92, gen2 0.85, gen3+ 0.70 — file is byte-identical to upstream). The
  `game.yml` 0.85 only governs `player_b` (opponent MCTS) and manual `mz play`.
  run.json gen-0 `td_discount: 0.95` is therefore correct upstream behavior.
  (Note: upstream README recommends λ ∈ [0.9, 0.95] while upstream's own
  curriculum anneals to 0.70 at gen3+ — an upstream-internal tension, not ours.)
- **Priors all FALSE in gen 0** is upstream's staging design:
  `curriculum.yml prior_schedule` turns heads on at binary=gen2,
  priority=gen3, target=gen4, opponent=never; defaults are all false. The
  `priority: true`/`binary: true` in `game.yml player_a` are manual-play
  defaults that the runner overwrites every gen. Upstream's own training log
  shows the win-rate inflection at gen2-3, exactly when priors activate.
- **prior_temperature** 1.5 both. **Noise** disabled both (upstream uses no
  Dirichlet noise or temperature sampling by design). **PUCT c = 1.0**
  hardcoded in the (stock) Java jars.
- Runner epoch constants (`EPOCHS_BOOTSTRAP=10`, `EPOCHS_ONLINE=1`) unchanged.

## 3. Upstream numerical baseline — what "working correctly" looks like

From upstream README.md, faq_goals.md, setup_guide.md, and
`results/roundrobin-trainlog.txt` (all tracked in the repo at origin/main):

**Win-rate trajectory** (round-robin train log, UWTempo vs 5 minimax
mono-color decks, 200-game evals per opponent, priors staged per curriculum):

| Gen | vs MonoB | vs MonoG | vs MonoR | vs MonoU | vs MonoW | Avg |
|---|---|---|---|---|---|---|
| 0 | .415 | .415 | .335 | .270 | .300 | **.347** |
| 1 | .405 | .410 | .425 | .285 | .280 | **.361** |
| 2 | .470 | .465 | .490 | .345 | .425 | **.439** |
| 3 | .565 | .520 | .485 | .455 | .485 | **.502** |
| 4 | .560 | .585 | .525 | .475 | .390 | **.507** |
| 5 | .600 | .540 | .600 | .470 | .410 | **.524** |
| 6 | .655 | .550 | .595 | .480 | .435 | **.543** |

i.e. roughly +2 pts gen0→1, then **+8 pts/gen through gen 3** (the jump
coincides with prior heads activating at gen 2-3), decelerating after gen 4.

**Headline claims (README/FAQ):**
- UWTempo vs the minimax pool: pure-minimax baseline WR 16%; RL reached **66%**
  (in that experiment, 1 generation = 1000 games).
- Final per-opponent: MonoB 48%, MonoG 34.5%, MonoR 57%, MonoW 52% — avg 47.9%
  (vs estimated human avg ~61%).
- **~20K MCTS games is enough for most decks**; full-depth games average
  **~18 s** on a mid/high-end GPU + 4.5 GHz quad-core.
- Throughput: **~250 games/hour** at 13 CPU threads and **300-sim budget**
  (~19.2 games/hour/thread); single-thread ~150 sims/s; ~100 batched
  inferences/s from the net server.

**Our measured equivalents:**
- Gen-0 (sessions 21-25, 200 games/opp, budget 300): R .365, G .225, B .260,
  W .261, U .450 — **avg .312**. Gen-1 attempts with the once-trained model:
  avg .361 / .327 / .345 across the three full aborted cycles, and s51-53 of
  the live attempt at .404/.269/.344. So we sit at roughly upstream's gen-0/1
  level — **the trajectory is flat because no training step has run since
  gen 0**, not because gen-0 output is anomalous.
- Throughput: sessions 51-53 took 4.9-5.4 h per 550 games at 6 threads →
  **~103-113 games/hour (~17.6 games/hour/thread — within ~10% of upstream's
  per-thread rate)**. The quality problem is not raw throughput but the 34%
  timeout-capped searches (Section 2, row 13).
- Budget math vs the 20K-games figure: at 550 games x 5 opponents/gen we spend
  2,750 games/gen; upstream reaches its gen-3 inflection on ~1,500-3,000 total
  games at comparable settings. We have already burned ~13,750+ games inside
  gen 1 alone on crash-looped attempts.

## 4. Prioritized fix list

### Restore BEFORE gen-1 training runs (i.e. immediately — the live attempt finishes soon)

1. **Fix the device regression** so the eval stage stops killing the runner:
   cache the device decision once per process (or move batches to
   `next(model.parameters()).device`) in `test.py`/`train.py`. Stopgap if no
   code change is wanted: set `eval_previous_model: false` in `run.yml` before
   the current attempt reaches the eval stage. Without one of these, attempt #7
   crashes identically and the crash loop continues.
2. **Quarantine the aborted-attempt files before the move/train stages run**:
   move sessions 26-50 (18 files, 597,188 states, ~4.4 GB) out of
   `data/UWTempo/ver1/testing/` (e.g. to `archive/`), leaving only the live
   attempt's sessions 51-55. Also move the 19 orphan pre-run files
   (sessions 1-20, 111,244 states) out of `training/` — they are invisible to
   the replay window and will otherwise persist for the entire run.
3. **Re-align the search regime**: either restore `search_budget: 1000`
   (author-shipped value) once serving is fast enough, or first fix eval
   serving so that <5% of searches hit the 4000 ms cap (currently 34.2%).
   Raising the budget while a third of searches already time out only converts
   more searches into timeout-capped ones.

### Before gen-3 (while the run is still salvageable)

4. Return `threads` to 4 (upstream default; upstream documents per-thread
   degradation above ~8) and stop mid-run edits of `run.yml` — the runner
   re-reads it on every restart while `run.json`'s snapshot silently goes
   stale (it still says `games_per_gen: 200`; live value is 550).
5. Reduce `games_per_gen` back toward 100-200 so a generation cycle (and hence
   the crash-recovery unit) shrinks from ~2.5 days to under a day; upstream's
   documented trajectory was achieved at 100-200 games/opp/gen (1000 in the
   long README experiment, but with working training between gens).

### Next run

6. Start a fresh `version` with an empty `data/<deck>/ver<N>/` directory and a
   clean bootstrap (`start_from_version: null`), as upstream's flow assumes —
   never self-seed a version from its own polluted directory.
7. Harden the runner against this failure class (upstream inherits the same
   flaw): on gen start, sweep `testing/` of any session id not recorded in
   `run.json` (or record reserved session ids at reservation time and archive
   unknown ids), so crash-looped attempts cannot silently enter the buffer.
8. Consider recording per-file provenance (gen, settings, attempt) inside the
   HDF5 files so the dataset loader can filter by bookkeeping instead of glob.
